# Default-off derived ROCm RGB-D producer

## Evidence and scope

The offline backend passed the installed generic SDK2.58.3 oracle on three synthetic cohorts and one captured1280x720 depth/1920x1080RGB cohort, ten diagnostic repeats each. All aligned raw-depth, unknown, XYZ, UV, packed RGB and texture-valid differences were zero. Warm native whole-backend mean8.441ms/p959.070ms versus SDK32.276/32.643ms. Initial interpreter/GPU setup and JIT are separate and must finish before source admission. These figures exclude ROS, packing, IPC and DDS; repeats are not new acquisitions. Frozen evidence is `rocm-projection/gpu-four-cohort-matrix.json`.

This next feature is an optional, default-off, **derived diagnostic producer**. It opens no SDK camera/device, owns no motors, publishes no TF/DeviceInfo, and grants no calibration, registration, recovery or execution authority. Existing camera and strict direct-camera consumers are unchanged. Root owns any later live activation/remapping.

## ABI and fixed ownership

- ROS remains native Python3.12. The explicit `/home/bjoern/miniforge3/bin/python` worker is Python3.13.12/Torch2.14.1+rocm7.2/HIP7.2.53211/gfx1151 Radeon8060S as measured in the offline proof. ROS code must not import Torch/Triton. Both source hashes, executable identity and the CPU compatibility shared-library hash are part of startup handshake metadata.
- Parent creates two fixed input slots and two fixed output slots using `os.memfd_create` plus shared `mmap`; descriptors are passed to the private subprocess with `pass_fds`. No pickle, Python shared-memory resource-tracker interaction, temporary image files or per-point IPC. Maximum input slot is1,843,200 depth bytes plus6,220,800 RGB bytes; maximum output slot is4,147,200 aligned-Z16 bytes plus18,432,000 packed PointCloud2 bytes (20bytes x921,600). Slots cannot resize from messages.
- Exactly one active worker job and one replaceable pending cohort. Active slots cannot be overwritten; queued work is never unbounded. Worker result has exact slot/sequence/generation and original immutable metadata digest. Release only after ROS output has acquired owned bytes; no later worker mutation may alter published messages.
- Socketpair messages are strict finite JSON with a fixed64KiB maximum. Startup/config/job/result/error/stop are fixed message kinds; no arbitrary code, paths, dimensions, allocation requests or caller caps from cohort messages. Worker calibration is admitted once; a changed profile/calibration/source generation clears history and requires explicit restart/requalification. Worker process failure/timeout makes status unavailable, no automatic restart or CPU fallback.
- Child environment is an allowlist with actual-UID home, explicit base interpreter/PATH and private temporary compiler/cache paths. No inherited ROS3.12/AMENT/Conda/Python/loader paths enter the child. The direct-file worker registers only its pinned pure-source directory as a private package, never the containing ROS3.12 site-packages parent. stdout/stderr are discarded; only bounded structured1024-character errors cross IPC, with no image payload logging.
- The parent opens a stable pidfd for its newly created private session before sending configuration. Linux>=6.9 `pidfd_send_signal(..., PIDFD_SIGNAL_PROCESS_GROUP)` support is probed with signal0; unsupported kernels fail before GPU import. Shutdown retires this exact pinned group even after leader exit, including compiler descendants; no numeric-PID/group signaling fallback or process inventory. [Kernel UAPI](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/uapi/linux/pidfd.h) and [kernel implementation](https://raw.githubusercontent.com/torvalds/linux/v6.12/kernel/signal.c) define the stable process-group scope.

## Input admission and lineage

- Inputs are existing native `16UC1` depth, `rgb8` color, their actual CameraInfo and exact depth-to-color transform. Preserve the received depth values including the camera's existing `clip_distance=1.2` filtering. Do not add/move clipping, fill unknown depth or refit extrinsics. Accept only currently supported zero-distortion calibration, dimensions, horizontal scan policy and4x4 maximum footprint; unsupported cases are unavailable.
- Require finite headers, correct optical frames and matching CameraInfo dimensions/K/D/encoding/step/storage. Fixed bounded receive buffers and sensor QoS. Pair actual original depth and color exposure stamps within40ms, matching existing marker/object default, each no future stamp and at most500ms old before admission and again before publishing. Carry both stamps; aligned depth and point cloud retain original depth stamp, RGB retains its own original stamp.
- Both selected CameraInfo original stamps independently pass the same no-future/500ms gates at admission and final publication. Only the proven five-zero-coefficient `plumb_bob` contract is supported; empty/other distortion schemas are rejected rather than relabeled. Actual optical TF must equal pinned R/T within1e-7, with no residual fitting.
- **Deduplicate both source exposure stamps.** A repeated native-depth frameset paired to a new RGB image is not a new independent cohort, nor vice versa. At most one scheduled/published cohort uses a given original depth or RGB exposure. Source rollback or changed frame/profile invalidates the generation; counters distinguish received, unique, admitted, superseded, stale and published.
- Require the exact current publisher GID of both original image callbacks and their unique graph endpoints. DeviceInfo/serial qualification belongs to the actual camera node/service endpoints associated with these source publishers. A fresh successful response must be tied to the captured camera source generation, not merely a matching node name or old serial result. Asynchronous renewal performs no callback filesystem or SDK I/O. Missing/mismatched/multiple publishers, parameter/context changes, stale identity or transport loss invalidate source buffers, pending work and in-flight publication eligibility.
- Derived status reports actual native camera source GIDs/serial/confirmation context plus its distinct producer generation and output publisher identity. It must never expose a fake camera DeviceInfo service. Until separately reviewed derived-producer attestation is added, existing recovery/periodic camera-source checks must remain unavailable for these output topics.

## Output semantics and hot path

- New private namespace `/so101_perception/rocm/`: aligned depth Image, aligned CameraInfo, colored PointCloud2 and bounded status/lineage String. No default remaps of `/camera/*`. Aligned depth uses original depth exposure, color optical frame and exact color K; native XYZ cloud uses original depth optical frame/exposure. No TF re-expression.
- Every output cohort has its own `/so101_perception/rocm/lineage` String, separate from the5Hz heartbeat `/status`. It includes the actual native four image/info GIDs and actual derived cloud/lineage/aligned-image publisher GIDs, both original image stamps plus both Info stamps, producer/source generations, sequence and the original DeviceInfo request context. Fixed six-module hashes remain unchanged in shape; separate `producer_node_sha256` pins the ROS logic. Calibration SHA is over original configuration file bytes, never reconstructed from a subset.
- Use the already qualified two-kernel/one-depth-H2D/one-packed-D2H backend unchanged. CPU compiled SDK-compatible occlusion/colorization follows readback. No per-ROI readback, per-point Python loops, per-point `.item()` or GPU synchronization calls. CPU array packing is vectorized.
- PointCloud2 is unordered/dense, little-endian, fields x/y/z at0/4/8 and float32-packed rgb at16, point_step20. Keep exactly the patched CPU texture-valid/positive-Z points; no new far filter, geometry sampling or fabricated colors. RGB bytes retain the original channel interpretation. Compare complete packed bytes and validity against a separately materialized CPU oracle before claiming parity.
- Root's live CPU wrapper layout audit found row_step still equal to full native capacity although width/data are packed. Emit the valid ROS row_step=width*20=data length; this deliberate metadata correction is separate from complete point-byte/order parity. Preserve the CPU inconsistency in overnight/live-cpu-pointcloud-layout.json rather than reproducing it.
- NumPy reference packing measured19.3ms at maximum921,600 points. The new **separate** bridge-runtime library links unchanged core `projection_compat.cpp` plus a bounded native wire-pack translation unit. A single allocation-free pass validates masks/finite positive selected XYZ and copies exact float/RGB bits with zero padding directly into the active output slot. Any fault yields no result. The old core compatibility binary and11 source pins remain unchanged; `compatibility_sha256` pins the entire new runtime. Its wire ABI is checked before GPU import.
- Parent output ownership uses `array('B').frombytes` on explicitly released bounded read-only mmap views. Both owned ROS arrays are complete before releasing the active slot; recycling slots or closing mmap cannot mutate prior ROS message data. This removes the intermediate bytes-to-array copy without sharing the worker's memory.
- Callback only validates bounded metadata/ownership, updates pairing and writes one pending slot. It never waits for GPU. A fixed timer consumes completed replies, rechecks source generation/deadline/original headers and publishes owned outputs. Finite worker watchdog and shutdown discard old results. Stop/shutdown affects only this private worker; no camera or arm process control.

## Implementation and qualification order

1. Add pure bounded cohort/slot protocol, pairing/dedup/source-generation state, vectorized PointCloud2 packing, and tests. Add private worker entrypoint with explicit enabled flag and fixed descriptors; no ROS imports there.
2. Add optional ROS node/script/launch, package dependency/install entries and schema documentation. Disabled launch creates no node/worker. Direct entrypoint defaults nonzero domain76/local-only and rejects invalid domain before ROS initialization.
3. Independent mandatory static/performance refinement **before any new GPU execution**: fixed allocation/ownership, one active/one pending, no per-point Python, no callback waits/hashing, deadlines checked after access, bounded IPC, original stamp/GID lineage and no default resource wake. CPU-only materialization/serialization/IPC benchmark at maximum dimensions, including input copying and output bytes; strict source/parity tests.
4. After ACK, bounded synthetic private worker GPU tests, including delayed worker, stale/future/replayed stamps, source replacement during inference, malformed IPC, generation swap, unknown masks and complete packed output equality. Preserve first failures. Native ROS synthetic publisher tests on a nonzero isolated domain measure unique exposure throughput and source-to-published age, not received-message rate. Include actual ROS serialization timing and cold startup separately.
5. Root review decides whether live read-only derived output may be enabled beside the existing path for a bounded comparison. No camera/owner restart, source impersonation, consumer freshness relaxation or control use is authorized by implementation or synthetic tests. Live camera changes remain root-only.

## Risks

The measured backend's26.7MB readback plus full output materialization and DDS may dominate at30Hz. We will report bytes/copies and CPU cost rather than assume throughput from GPU kernels. Fixed pairing can reject legitimate unsynchronized images, which is preferable to stamp refresh or duplicate proof. Source lineage for derived publishers is a new explicit contract; leaving control consumers unavailable is intentional until that contract is independently qualified. No ROS bridge result qualifies depth scale, model/TCP, tag attachment or physical pick/place.

## Build and review commands

`bash tools/build_rocm_bridge_runtime.sh` creates only a new private `ros2/.cache/rocm-projection/bridge-runtime.so` and source/output manifest; it never executes GPU code or overwrites core `compat.so`. Production worker must receive this runtime explicitly, not the core-only library.

CPU-only focused tests are `tests/test_rocm_transport.py`, `tests/test_rocm_worker_protocol.py`, `tests/test_rocm_wire_pack.py` and `tests/test_ros_rocm_rgbd.py` (the last uses isolated native ROS with an explicit CPU fake worker). `tools/benchmark_rocm_transport.py --ros --wire-pack-library .../bridge-runtime.so --owned-ros-arrays` measures real message serialization plus packing/ownership/IPC proxies, without GPU or DDS. `tools/benchmark_rocm_worker.py --gpu ... --ros` is a separate explicitly gated actual private-worker validation tool; it must not run until independent final-source/static/performance ACK and root authorization.
